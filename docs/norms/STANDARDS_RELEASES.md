# STANDARDS_RELEASES — Release management

> Status: draft v0.1
> Scope: every published CABOC package.

## 1. Tools

- **Changesets** (<https://github.com/changesets/changesets>) for
  semver bumps + CHANGELOG generation.
- **GitHub Releases** for tagged release artefacts.
- **npm provenance** (or sigstore signing) for published packages.

## 2. Workflow

1. A PR that affects published behaviour adds a changeset:
   `pnpm changeset` → describes the change at major / minor / patch
   granularity per touched package.
2. CI blocks merge if a published-package diff lacks a changeset (lint
   rule).
3. Changesets accumulate on `main` between releases.
4. A maintainer opens a "release" PR: `pnpm changeset version` applies
   bumps + generates `CHANGELOG.md` entries per package.
5. The release PR is squash-merged to `main`.
6. CI publishes the new versions: `pnpm changeset publish` + creates
   GitHub Releases + signs.

## 3. Semver discipline

Per package:

- **Major** — breaking change to public API or routine schema.
- **Minor** — backwards-compatible feature, schema loosening,
  new norm.
- **Patch** — bug fix, doc fix, dep bump without behaviour change.

A spec version bump (`caboc-llm/0.1.0` → `0.2.0`) on the runtime skill
triggers at least a minor bump on every consumer of that spec version.

## 4. CHANGELOG.md

Each published package owns a `CHANGELOG.md` at its root, generated by
Changesets. Format:

```
# @caboc/cli

## 0.2.0

### Minor Changes

- abc1234: Add `caboc inspect --json` flag.

### Patch Changes

- def5678: Fix relative path resolution on Windows.
```

The root repo `CHANGELOG.md` aggregates monthly summaries written by
the release maintainer (manual prose, not generated).

## 5. Versioning the spec

The runtime skill declares `spec_version: caboc-llm/0.1.0` in its
frontmatter. Bumps follow semver:

- Major — breaking change to body grammar, event types, or
  agent frontmatter contract.
- Minor — additive feature: new keyword, new event type,
  new optional frontmatter field.
- Patch — clarifications, doc fixes.

A routine declaring `spec_version: caboc-llm/0.1.0` runs on any runtime
implementing the same major version.

## 6. LTS commitments

- v0 (any v0.x): no LTS commitment; breaking changes possible between
  minors with a deprecation note.
- v1 onwards: each major receives security fixes for 12 months after
  the next major is released.

## 7. Release artefacts

A GitHub Release for `@caboc/cli@1.0.0` includes:

- The npm tarball reference.
- A signed checksum.
- The CHANGELOG section for this version.
- A SBOM (CycloneDX 1.6) attached as a release asset.

## 8. Yanking a release

- npm: `npm deprecate @caboc/<pkg>@<bad-version> "use @caboc/<pkg>@<good-version>"`.
- GitHub Release: mark as "draft" or convert to a pre-release with a
  notice.
- A yanked version stays installable for in-place pinning but warns on
  install.

## 9. Pre-releases

- Tags: `0.1.0-rc.1`, `0.1.0-rc.2`, `0.1.0`.
- npm dist-tag: `next` for `*-rc.*`, `latest` for stable.
- Pre-releases for routines + skills follow the same convention.

## 10. Release announcements

- A blog post on the project site (`docs-site`) accompanies every minor
  and major release.
- Patch releases ship silently (CHANGELOG only).
- Breaking changes are announced 30 days in advance via a deprecation
  notice in the previous minor.
